# 评估门禁 —— 检索质量如何被度量（以及如何不被宣称）

这是本展示仓库中最重要的一篇文档，因为检索质量是这个项目里最容易被夸大的东西。

## 简短版

| 声明 | 状态 |
|---|---|
| Success@20 ≥ 80% | **生产目标。未达成。** |
| 评估管线端到端可用 | **是**——由 100 条查询的门禁验证 |
| 高级检索能提升质量 | **未获证明，因此关闭** |

## 1. 今天存在什么

仓库附带一个**100 条查询的合成查询集**（`examples/benchmark_queries.json`），每个条目形如：

```json
{
  "id": "Q001",
  "query": "realistic close heavy rusty metal gate opening slowly",
  "category": "heavy",
  "relevant_file_ids": []
}
```

查询类别：

| `large` | 8 |
| `small` | 8 |
| `heavy` | 8 |
| `monster` | 4 |
| `car` | 4 |
| `plastic` | 4 |
| `industrial` | 4 |
| `soft` | 4 |
| `forest` | 4 |
| `electricity` | 4 |
| `ceramic` | 4 |
| `snow` | 4 |
| `paper` | 4 |
| `distant` | 4 |
| `rifle` | 4 |
| `fast` | 4 |
| `close` | 4 |
| `metal` | 4 |
| `underwater` | 4 |
| `cloth` | 4 |
| `wet` | 4 |
| `wooden` | 4 |

**关键细节：** 所有随仓库提供的条目中，`relevant_file_ids` 都是空的。真值标注需要有授权的 10k+ 音效语料作为判断依据，而这不是本项目能够提供的。因此这个合成集当前验证的是**评估机制**——解析、候选生成、指标计算、报告——而不是检索质量。

任何人在未先针对真实语料填充 `relevant_file_ids` 的情况下引用本仓库的质量数字，引用的都只是测试架本身的产物。

## 2. 达到生产质量需要什么

1. 使用**有授权的 10k+ 音效语料**填充 `relevant_file_ids`。
2. 运行基准测试并达到 **Success@20 ≥ 80%**。
3. 在高级检索能被证明有帮助之前，保持它处于默认拒绝状态（见下文）。

在第 1 步完成之前，本项目给出的任何 Success@20 数字都没有意义。

## 3. 默认拒绝规则（ADR-004）

交叉编码器、微调嵌入、个性化重排、可视化地图、自动分层与场景分析**默认关闭**，并且保持关闭，除非 `benchmark/reports/results.json` 记录到：

- 至少**两个点的 Success@20 提升**，且
- 候选延迟**低于 500 毫秒**。

**缺少证据就是硬性关闭开关，而不是默许。** 正是这项设计决策让项目保持诚实：一个没被实现的功能不可能悄悄变成一个声明。

## 4. 其他确实在运行的校验

| 检查 | 命令 |
|---|---|
| 静态检查 | `ruff check .` |
| 测试与覆盖率 | `pytest --cov=sfx` |
| 规模基准测试 | `python scripts/benchmark_scale.py --count 10000` |

注意，规模基准测试度量的是*管线在规模下的行为*（吞吐、延迟），这与检索*质量*是两个不同的问题。

## 5. 在本展示仓库中应当如何做质量声明

- 可以说：「评估测试架与门禁存在，且高级功能被挡在可度量的改进之后。」
- 可以说：「一个 100 条查询的合成门禁验证了评估管线。」
- 不可以说：「检索达到 80% Success@20」，或任何暗示生产目标已达成的话。
- 不可以说：把合成门禁当作真实音效库检索质量的证据。

## 6. 值得展示的已知失效模式

CLAP 对描述性、基于声音的措辞检索得好，对隐喻性或叙事性措辞检索得差。这个系统未来任何演示都应当包含失败案例——包括那些正确文件从未被返回的查询——因为门禁存在的意义正在于此。
