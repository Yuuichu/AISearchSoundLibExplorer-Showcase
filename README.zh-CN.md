# AI SFX Explorer —— 面向音效库的本地优先语义检索

面向大型音效库的自然语言检索：描述你要的声音，拿回文件**以及文件内的时间范围**，试听它，再放进工程里——全部在本地运行，源音效库严格只读。

## 为什么做这个

音效库会膨胀到文件名和目录结构再也承担不起检索职责的程度。设计师知道自己想要「沉重、生锈的金属大门缓慢打开」，而音效库只知道 `MTL_GATE_Rusty_Open_01.wav`。常见的应对要么是标签纪律（会逐渐失效），要么是把音效库上传到云服务（对授权素材或客户素材来说不可接受）。

我想同时满足三个特性：**本地优先**（音频不离开本机）、**对源音效库只读**（检索工具绝不能破坏素材库）、以及**片段级结果**（一段 40 秒的环境声中包含好几个可用的事件；返回整个文件不算答案）。

## 功能概览

- **自然语言检索**，提供三种模式：`keyword`、`semantic`、`hybrid`。
- **片段级检索。** 长文件以重叠片段方式建立索引，因此命中指向文件内部的一个时间范围，而不是整个文件。
- **双路召回 + 排序融合。** 语义（CLAP）候选与元数据候选独立召回，再用 Reciprocal Rank Fusion 加上精确匹配加分合并。
- **REAPER 客户端。** 搜索、预览、相似、收藏、插入、片段插入与键盘导航，全程不离开 DAW。
- **覆盖整个工作流的管线：** 可续跑的索引任务、波形与 Range 预览、UCS 浏览、集合、收藏、反馈采集、历史记录、CSV 导出，以及 OpenAPI 接口。
- **非破坏性元数据。** 写元数据会生成一个 `.sfx.json` 侧车文件；源文件及其内嵌标签永不被修改。

## 工作流

```text
Natural-language query ("heavy rusty metal gate opening slowly")
        |
        v
query parsing  (optional LLM query planning — disabled by default)
        |
        +-------------------------+
        v                         v
  CLAP text embedding       metadata / keyword index
        |                         |
        v                         v
   Qdrant (HNSW)              SQLite
        |                         |
        +---------> RRF fusion <--+
                   (k = 60, + exact-match bonus)
                        |
                        v
        file hit + best matching time range
                        |
                        v
        REAPER client  /  HTTP API  /  debug UI
```

## 技术要点

- **三层存储，权威顺序是刻意设计的。** SQLite 是文件、元数据、任务、反馈、历史与集合的唯一事实来源；Qdrant 存放可替换的向量索引和最小化的过滤载荷。因此重建或迁移向量库不可能丢失用户数据。
- **索引身份带版本。** 集合名称包含嵌入模型与预处理身份，因此更换嵌入模型会创建新集合，而不是静默混入不兼容的向量。
- **默认拒绝（fail-closed）。** 如果 CLAP 无法加载，系统会拒绝建立索引，而不是悄悄用确定性测试向量灌满生产音效库。确定性提供方仅为开发和 CI 存在，且需要显式开关。
- **有界的片段索引。** 超过短音频阈值的文件使用重叠窗口（10 秒窗口 / 5 秒步长，上限 60 个片段），检索时把片段命中收敛回文件，同时保留最佳匹配范围。
- **可续跑的索引。** 任务在执行中持续设置检查点并每 50 个文件报告一次进度，因此重跑会安全地续处理那些已扫描但尚未嵌入的文件。
- **源音频只读。** 音效库永不被写入；用户元数据与 AI 元数据存放在 SQLite 中，导出时写侧车文件。
- **把 LLM 用在它该在的位置。** 只用于查询规划，默认关闭；云提供方只会收到查询文本——绝不收到音频，也绝不收到音效库索引。
- **架构决策以 ADR 形式记录下来**（见 `docs/adr-summary.zh-CN.md`），包括那些会约束未来工作的决策。

## 局限与边界

以下内容是有意写明的，因为检索质量很容易被夸大：

- **生产质量目标尚未达成。** 仓库把 **Success@20 ≥ 80% 记录为生产目标**。该目标**尚未**达成：要达到它，需要在有授权的 10k+ 音效语料上填充相关性真值。今天存在的是一个**验证评估管线的 100 条查询合成门禁**，而不是关于真实音效库检索质量的声明。
- **规模是设计目标，而非已证明的事实。** 架构面向数十万文件的音效库；本地实际建立过索引的最大音效库远小于这个量级。
- **高级检索能力被刻意关闭。** 交叉编码器、微调嵌入、个性化重排、可视化地图、自动分层与场景分析一律保持关闭，除非基准测试记录到至少两个点的 Success@20 提升，且候选延迟低于 500 毫秒。缺少证据被视为硬性关闭开关。
- **CLAP 有真实的失效模式。** 描述性比喻（「一扇已经放弃的门」）检索效果很差。失败案例是诚实图景的一部分，应当与成功案例一同展示。
- **CUDA 是可选项但建议启用。** CPU 嵌入是正确的，只是慢；要有意义的语义质量，必须使用生产级 CLAP 提供方。
- **本展示仓库不附带任何音频内容**，这是刻意的。
